§2 Processing workloads · The situation

Debiting 3,000 accounts at midnight

A savings product. Every midnight, we move money for everyone who set up a mandate.

@cron("0 0 * * *")
def process_mandates():
    mandates = Mandate.objects.filter(active=True)   # 3,000 rows in memory
    results = []
    for mandate in mandates:
        results.append(debit_customer(mandate))      # a network call, each time
    send_summary(results)
  1. Blast radius — #412 raises, and #413 to #3,000 never run
  2. Retries are all-or-nothing — re-running debits whoever already paid
  3. Memory grows with the data — every row, every result, held all night
  4. No visibility — one log line for 3,000 financial operations

A savings product: people set up a mandate saying how much to save and how often, and every midnight a cron job moved the money for all of them. It had run this way for years, and it was one of the first things I was asked to fix after joining. The problem is not the code — it is that the entire night is a single unit of work.

70s. Say "three thousand" out loud — it was already hurting at three thousand. Point 4 is the one that actually hurt: support asks what happened to a customer and you cannot answer.

§2 Processing workloads · What we did & the concept

One job per mandate

@cron("0 0 * * *")
def enqueue_mandates():
    ids = Mandate.objects.filter(active=True).values_list("id", flat=True)
    for mandate_id in ids:
        process_mandate.delay(mandate_id)      # 3,000 independent jobs

@celery.task(bind=True, max_retries=3, autoretry_for=(ProviderError,))
def process_mandate(self, mandate_id):
    debit_customer(Mandate.objects.get(id=mandate_id))

Whatever you made a unit of work is the only thing you can retry, observe, or scale.

Unit = the whole nightUnit = one mandate
one failure stops everythingone failure stops one customer
retry the whole batchretry that one job
memory = all rowsmemory = one row
one log linea job id and status per customer

That was work trapped inside a loop. The next one had already been moved off the request — or so we thought.

The fix is to change what a unit of work is. The cron no longer does anything except decide what should run — it enqueues one job per mandate and stops. A worker picks up each one independently. Now a single failure fails a single customer, retries happen per mandate and automatically, memory is one row at a time, and every customer has a job id and a status you can look up. That is the general lesson: whatever you made a unit of work is the only thing you can retry, observe, or scale. The same idea applies one level up — an ETL pipeline written as one big script has these exact four problems, and splitting it into steps is what lets you re-run step four without redoing one through three.

75s. The cron now only decides WHAT runs; workers do it. End on the bridge — it sets up the next story as a twist, not a repeat. Aside if time: same idea one level up — an ETL pipeline as one big script has the same four problems. Split it into steps and you can re-run step 4 alone.

Three services, one loop

┌──────────┐         ┌───────┐         ┌──────────┐   HTTP    ┌────────────┐

└──────────┘         "step 3 done, 812 flagged"
Kafka sits between core and the gateway. But the hop that matters — gateway to automation — is a synchronous HTTP call.

Core publishes "run step 3" to Kafka. The gateway consumes that message and turns it into an HTTP request. Automation does the work, then calls core back over HTTP. Core reads the result, decides step 4 is next, and publishes again — round and round until the workflow is finished. Note where the queue is: between core and the gateway. The gateway then waits, synchronously, for automation to answer.

60s. Trace all four hops with your hand. Plant the last line hard — the queue is early in the chain and the expensive work is two hops past it. That is the whole failure, and nobody sees it coming.

§2 Processing workloads · What broke

Then core started batching

10 messages a second  →  200,000 at once.

core ──▶ Kafka ──▶ gateway ──▶ automation
          200,000     drains      200,000 synchronous
          messages    flat out    HTTP requests
  • Kafka absorbed the burst — that's its job
  • The gateway drained flat out, one HTTP call per message
  • Automation pinned at 100% CPU and restarted in a loop
  • The callbacks core was waiting on were never sent

Core changed from a trickle to a flood — around two hundred thousand messages onto Kafka at once. Kafka handled it perfectly, which is exactly what a log is for. The gateway then drained that backlog as fast as it could and turned every single message into a synchronous HTTP call. Automation saturated, restarted, and started dropping requests — including the callbacks core needed to advance the workflow. The failure fed itself, because the callbacks travelled the same broken path.

Here is the code that caused it. FastAPI's BackgroundTasks looks like the fix — you return a 202 immediately and the work happens after the response is sent. But it happens in the same process. A synchronous handler gets Starlette's threadpool, an async one runs on the event loop; either way it is the same CPU and the same memory that is supposed to be accepting the gateway's requests, and nothing survives a restart. We had made the response fast. We had not moved the work. And the sting is that we already had Kafka — it just sat two hops upstream of the expensive part. A queue only protects the hop it sits in front of.

§2 Processing workloads · What we did

Made the synchronous hop cheap

┌──────────┐   ┌───────┐   ┌─────────┐  HTTP   ┌────────────┐   ┌───────┐
│   core   │──▶│ Kafka │──▶│ gateway │────────▶│ automation │──▶│ Redis │
│ (Django) │   └───────┘   └─────────┘◀────────│  (accepts, │   └───┬───┘
│          │                          202 in   │  enqueues) │       │
│          │                          ~5ms     └────────────┘       ▼
│          │                                          ┌──────────────────┐
│          │◀── POST /callbacks/step-complete ────────│ celery workers ×N│
└──────────┘        "step 3 done, 812 flagged"        │  (own machines)  │
                                                      └──────────────────┘
@app.post("/steps/3", status_code=202)
def auto_label(req: StepRequest):
    label_conversations.delay(req.project_id, req.batch_id)   # hand it off
    return {"status": "queued"}                               # ~5ms

@celery.task(bind=True, max_retries=3)
def label_conversations(self, project_id, batch_id):
    flagged = run_labelling_model(project_id, batch_id)
    core.step_complete(project_id, step=3, needs_review=flagged)   # ← callback

The gateway's call now returns in milliseconds, so it stops mattering how fast it drains Kafka. And the callback comes from the worker that actually did the work — the only thing that knows when it's really finished.

Two changes. Automation now does nothing but validate the request, hand the job to Celery, and return — about five milliseconds — so it no longer matters how fast the gateway drains Kafka. And the callback moved to the worker, because the worker is the only thing that actually knows when the work has finished. Note the two arrows going back into core: the 202 means "I have accepted this", and the callback means "it is done". Those are different statements, and the old design conflated them.

65s. Two moves: the synchronous hop got cheap, and the callback moved to the worker. Concurrency is now a number we set, not whatever the load happens to be.

§2 Processing workloads · What we did next

Not every step costs the same

Stripping PII takes a second. Labelling takes minutes. One queue, and the quick job waits behind the slow one.

celery_app.conf.task_routes = {
    "tasks.label_conversations": {"queue": "heavy"},   # CPU-bound, minutes
    "tasks.package_dataset":     {"queue": "heavy"},   # big files, lots of memory
    "tasks.strip_pii":           {"queue": "light"},   # quick, high volume
    "tasks.notify_client":       {"queue": "light"},
}
queue: heavy   ──▶  a few large instances      celery -Q heavy -c 4
queue: light   ──▶  many small, shared ones    celery -Q light -c 20

Two pools, scaled independently — a labelling backlog adds heavy workers and touches nothing else.

Once everything was on a queue, a second problem appeared: all the steps shared one. Stripping personal data from a batch takes about a second. Labelling a batch takes minutes. On a single queue the quick job sits behind the slow one — head-of-line blocking — and the whole system reads as "slow". So we split the queues by how expensive the work is, and gave each queue its own pool: a few large machines for the heavy work, many small shared ones for the light work.

60s. Say the shape of the problem first: head-of-line blocking. A one-second job stuck behind a twenty-minute job is pure waste, and it looks like "the system is slow". This is the same isolation idea as bulkheads in the next section — but here it's about matching the machine to the work, not just keeping failures apart.

Everything so far pushes work off the critical path — into queues, workers, schedulers. Which means it now runs somewhere you are not watching. And sometimes it runs twice.

Pick by the question you are answering, not by the tool's reputation. If you need work run now and independently, that is a task queue. If you need ordered steps on a schedule with the ability to re-run step four on its own, that is an orchestrator. If you need messages routed to workers and consumed once, that is a broker. If you need many consumers reading the same stream with the ability to replay from last Tuesday, that is a log. And if you have Postgres and thirty thousand users, a table with FOR UPDATE SKIP LOCKED is very often the right answer. Most of the pain I have seen came from bending one of these into another. §3 Reliability · Why it broke

Why the same work runs twice

Queues guarantee at least once — not exactly once. The gap shows up at failure boundaries:

  1. A retry after a timeout — it went through, you never heard back ← the common one
  2. A worker dies before it acknowledges — the broker re-delivers
  3. A webhook is redelivered — WhatsApp, Instagram, Stripe all document this
  4. Two schedulers fire the same job ← what happened to us
  5. The client sends it twice — a double-click, or its own retry
Most days none of this happens. That's the trap — "most days" isn't a guarantee, and here it is somebody's money.

This is the part people get wrong in both directions. A queue does not duplicate constantly — most days it hands each message to exactly one worker, and that is what happens. But the guarantee it makes is at-least-once, not exactly-once, and the gap opens at failure boundaries. The most common cause by far is a retry after a timeout, where the call actually succeeded and you simply never got the answer. Webhook providers redeliver by design. And in our case, two schedulers fired the same job. The argument is not frequency, it is consequence: rare is fine for a thumbnail cache and not fine for a debit.

65s. Be precise — do NOT claim queues duplicate constantly, because they don't, and someone in the room knows it. The argument is rarity vs. consequence: rare is fine for a thumbnail cache, and not fine for a debit. Next slide covers what people reach for to prevent it.

§3 Reliability · What people try first

Three ways to stop two runners colliding

Two servers woke up. How do you stop the second one?

1  ·  Take a lock — pessimistic

with redis.lock("cron:mandates"):   # only one server gets in
    process_mandates()

Stall past the lock's timeout and it expires while you're still working.

2  ·  Check a version — optimistic

UPDATE mandates SET status='running' WHERE id=42 AND version=7;
-- 0 rows updated = someone beat you to it

Protects the row. Not the debit you already sent the provider.

3  ·  Split the work — partitioning

if ring.owner(mandate_id) == this_node:   # each node owns a slice
    process(mandate_id)

Ownership moves when a node joins or leaves.

All three make a second run less likely. None of them makes a second run safe.

Two servers woke up at midnight. How do you stop the second one? Pessimistic locking takes a lock first and makes everyone else wait — but if the holder stalls past the lock's timeout, the lock expires while it is still working, and now there are two runners and neither knows. Optimistic locking checks a version at the moment you write, and zero rows updated means somebody beat you — but that protects the row you versioned, not the debit you already sent to a payment provider. Partitioning avoids the collision entirely by hashing each job onto a ring so every node owns a slice — but ownership moves whenever a node joins or leaves, and during that shuffle two nodes can both believe they own the same key. Every one of these makes a second run less likely. None of them makes a second run safe.

80s. Define each in a line — the room has heard the words, not necessarily used them. Consistent hashing: the ring means adding a node reshuffles a slice, not everything. Land the last line and pause. The next slide is the answer. If asked "so are locks useless?" — no. Use them to avoid wasted work. Just don't use them as your correctness guarantee.

§3 Reliability · Why it matters

What a second run actually costs

   THE OPERATION                      RUN IT TWICE
   ─────────────────────────────────────────────────────────
   SET status = 'paid'                nothing changes
   balance = balance - 4,200          debited twice
   send_sms("₦4,200 debited")         told twice
   INSERT INTO payouts (...)          paid twice

Only the first line is safe to repeat. It sets a value. The rest apply a change — and a change applied twice is a different number, a confused customer, or money out the door.

A payment provider sends payment.succeeded. The network blips and it redelivers — which is documented behaviour, not a bug. We credit the wallet twice, and we were paid once. Nothing in our code was wrong. We just had no way to say "I have already seen this one."

This is the part worth being concrete about, because "runs twice" sounds harmless until you look at what the operation actually is. Setting a status to paid is safe to repeat — run it a hundred times and the row says paid. But almost nothing else is. Subtracting from a balance twice takes the money twice. Sending an SMS twice tells the customer twice. Inserting a payout row twice pays somebody twice. The difference is whether the operation sets a value or applies a change, and applying a change twice is always a different outcome. Here is the one that actually costs you: a payment provider sends payment dot succeeded, the network blips, and it redelivers the webhook — which is documented behaviour on every provider I have used, not a bug. Without protection you credit that wallet twice, and you were only ever paid once. Nothing in the code was wrong. We simply had no way of saying "I have already seen this one".

§3 Reliability · The concept

Idempotency, and where the key comes from

Idempotent — running it twice leaves the same result as once.

key = str(uuid4())                     # new key every attempt — useless
key = f"{mandate_id}:{run_date}"       # same key every attempt

Derive the key from the work, not from the attempt.

Good keys

  • mandate_id + run_date
  • order_id
  • the provider's message id

Bad keys

  • anything with a timestamp
  • a fresh UUID
  • the hostname or retry count
Where you can, rewrite the work so it sets a value instead of applying a change — an upsert, a delete by id, SET status = 'paid'. Then the key stops being the only thing standing between you and a double charge.

Idempotent means running something twice leaves the same result as running it once. The part people get wrong is the key. If you generate a fresh UUID on each attempt, every retry looks like new work and the index never fires. The key has to be derived from the work itself — the mandate and the date, the order id, or the message id a webhook provider hands you for free. Anything containing a timestamp, a hostname or a retry count is not a key, it is a serial number.

60s. Webhooks hand you a free key — the provider's message id. Most immediately useful slide in the talk.

§3 Reliability · What we did

Backoff, jitter, and a cap

@celery.task(
    bind=True,
    autoretry_for=(RequestException,),   # only what's actually retryable
    retry_backoff=True,                  # 1s, 2s, 4s, 8s ...
    retry_jitter=True,                   # randomise, so clients desynchronise
    retry_backoff_max=600,               # stop doubling at 10 minutes

Four flags on one decorator. Exponential backoff gives the dependency room to recover. Jitter randomises the wait so clients desynchronise instead of returning in lockstep — this is the part people skip, and it is the part that actually breaks the herd. The cap stops a task retrying for three days. And autoretry_for matters: retry a 500, never retry a 400, because a bad request will be bad every time.

§3 Reliability · The concept

Failing well when a dependency is down

CLOSED  ──5 failures──▶  OPEN  ──60s──▶  HALF-OPEN
   ▲                      │                  │
   └──────success─────────┴───one probe──────┘
  • Circuit breaker — once you know it's down, stop calling. Fail fast, or route elsewhere.
  • Timeouts on every network call — requests defaults to none. One hung socket holds a worker forever.
  • A queue per dependency — a stuck SMS provider must not stop payments.

Three things, in order of how often they save you. A circuit breaker means that once you know a service is down you stop calling it — failing immediately instead of burning a worker for a thirty-second timeout. Timeouts on every network call, because the requests library defaults to no timeout at all and one hung socket holds a worker forever. And a separate queue per dependency, so a backed-up SMS provider cannot stop payments from processing. We split notifications into their own service for exactly that reason — we just did not have the word "bulkhead" for it at the time.

55s. §3 should end around 18:30.

§3 Reliability · Designing for it

An open circuit is a chance to go elsewhere

def charge(amount, ref):
    for provider in PROVIDERS:                  # primary, then fallback
        if breaker.is_open(provider.name):
            continue                            # known down — skip it
        result = provider.charge(amount, ref)
        record(ref, provider=provider.name, external_id=result.id)
        return result
    raise AllProvidersDown

Only works if you built for it before the outage:

  1. One interface, many adapters — no if provider == "x" in business logic
  2. Normalise on the way back in — they won't agree on what "pending" means
  3. Record who processed what — their name, and their reference id
Point 3 isn't bookkeeping — refunds and disputes go back to whoever moved the money. Your idempotency key stays yours.

Retries, replays, failovers — every one of them means the same work reaching your data more than once. So the data has to survive it.

Failing fast is good; failing over is better, when someone else can do the work. In Nigerian fintech, having more than one payment provider is normal rather than exotic. But failover only works if you built for it beforehand: one interface with many adapters, so business logic never branches on which provider answered; normalised responses, because two providers will never agree on what "pending" means; and a record of which provider processed each transaction, with their reference id. That last one is not bookkeeping — refunds, disputes and reconciliation all go back to whoever actually moved the money, and the two providers have completely different id spaces. Your idempotency key stays yours.

75s. More than one payment provider is normal in Nigerian fintech, not exotic — the room will recognise this instantly. Say it plainly: switching providers must never mean charging twice.

§4 Databases · Why it broke

The check was correct. It wasn't atomic.

   request A                          request B
   ─────────                          ─────────
   read balance              5,000
                                      read balance              5,000
   check 5,000 >= 4,200        ok
                                      check 5,000 >= 4,200        ok
   balance = balance - 4,200     800
                                      balance = balance - 4,200  −3,400

Between the read and the write, someone else read the same number. Both requests were individually correct — and ₦8,400 left an account holding ₦5,000.

This is a race condition: the result depends on the order two things happen to interleave.

Two requests read the same balance of five thousand. Both check it against a forty-two hundred withdrawal, and both pass, because at the moment each of them looked, the money was there. Then both apply their decrement. Eight thousand four hundred leaves an account that held five thousand. Neither request did anything wrong on its own — the bug lives in the gap between the read and the write. That gap is what a race condition is.

§4 Databases · What we did

Make the check and the write one operation

-- check and write in a single statement
UPDATE accounts SET balance = balance - :amt
 WHERE id = :uid AND balance >= :amt;     -- 0 rows updated = declined
# or hold the row while you decide
acct = db.query(Account).filter_by(id=uid).with_for_update().one()
-- and a backstop the application cannot forget
ALTER TABLE accounts ADD CONSTRAINT bal_nonneg CHECK (balance >= 0);

The single statement is the right default. The constraint costs nothing and saves you when someone adds a new code path next year.

Three ways to close the gap. The single conditional UPDATE is the right default: the check and the write happen in one statement, and zero rows updated means declined. SELECT FOR UPDATE holds the row while you decide, which is useful when the decision is more complicated than one comparison. And a CHECK constraint costs nothing and is the one that saves you in two years, when somebody adds a code path that forgets the other two.

§4 Databases · A different system

What belongs inside a transaction

Another fintech: every withdrawal sends an SMS. We saw both halves fail, separately.

Locked for someone else's outage

with db.begin():
    order.status = "paid"
    provider.charge(...)   # 200ms… or 30s
    send_email(...)

Locked for microseconds

with db.begin():
    order.status = "paid"
    db.add(Outbox(
        topic="order.paid",
        payload={"id": order.id}))

Never hold a lock across a network call you don't control.

But take it out and the two can now disagree. Writing the intent in the same transaction is the outbox.

Another fintech: every withdrawal fires an SMS, and the money moving and the message going out have to agree. We saw both halves fail separately. A transaction is all-or-nothing, and it holds locks for its entire duration — so a network call inside one means you are holding a row lock for as long as somebody else's server takes to answer. Take it out. But then the two can disagree: the commit succeeds and the message is never queued, or the message goes out and the commit rolls back. Writing the intent into the same transaction, and delivering it separately, is the outbox pattern.

§4 Databases · The concept

Why the outbox works, and who drains it

commit succeeds  ──▶ process dies       ──▶ the SMS is never sent
SMS sent         ──▶ commit rolls back  ──▶ you told them about money
                                            that never moved

Put the intent in the same transaction as the change and those two can never disagree. Delivery becomes a separate problem, with its own retries.

A cron that flushes it

SELECT id, topic, payload FROM outbox
 WHERE published_at IS NULL
 ORDER BY id LIMIT 100
 FOR UPDATE SKIP LOCKED;
for row in batch:
    broker.publish(row.topic, row.payload)
    mark_published(row.id)

Every few seconds. No new infrastructure. SKIP LOCKED lets several run at once.

Change data capture

   postgres WAL
        │
        ▼
   ┌──────────┐
   │ Debezium │──▶ broker
   └──────────┘

Tails the replication log instead of polling. Lower latency, no query load — and one more system to operate.

Publish, then mark. A crash in between duplicates an event rather than losing one — and duplicates you already handle. Not a trigger: a trigger runs inside your transaction and can't safely make a network call.

The reason the outbox is worth the trouble is that it removes a whole class of disagreement. Without it, either the commit succeeds and the message is never sent, or the message goes out and the commit rolls back — and you have just told a customer about money that never moved. Writing the intent into the same transaction as the change means the two commit together or not at all. Delivery then becomes a separate problem with its own retries, which is a much easier problem. Draining it has two sensible answers. The simple one is a cron that runs every few seconds, selects unpublished rows with FOR UPDATE SKIP LOCKED so several copies can run without fighting, publishes each row and marks it done — no new infrastructure, and it is genuinely fine for most systems. The scaled-up one is change data capture, where something like Debezium tails the Postgres write-ahead log and publishes for you: lower latency and no polling load, at the cost of another system to operate. Whichever you pick, publish before you mark, so a crash duplicates an event rather than losing one — duplicates are the failure you already handle with idempotency keys. And do not reach for a database trigger: a trigger runs inside your transaction and cannot safely make a network call.

75s. Everyone says "outbox" and nobody shows the part that sends anything. Give the cron version the weight — most of the room does not need Debezium. SKIP LOCKED callback to the tool table in §2.

§4 Databases · Why it breaks things

A slow migration doesn't just run slowly

  • It's one transaction — rows stay locked until the whole migration commits, not until that statement finishes
  • Some of it blocks readers too — SET NOT NULL takes ACCESS EXCLUSIVE: no writes, no reads
  • Locks queue — and that's the real killer. You wait behind a long query; everything else waits behind you
SET lock_timeout = '3s';   -- fail fast instead of building a queue behind you
Migrations change structure, and should be quick. Moving data is a separate job — batched, pausable, resumable.

Three reasons. It runs in one transaction, so every row the UPDATE touches stays locked until the whole migration commits, not until that statement finishes. Some of it blocks readers as well as writers — SET NOT NULL and table rewrites take an ACCESS EXCLUSIVE lock. And the one people have not thought about: locks queue. Your migration waits behind whatever long-running query is already there, and every request arriving afterwards waits behind your migration. A migration that only needs two hundred milliseconds can still stall the site for a minute purely because of what it got stuck behind. Setting a lock_timeout makes it fail fast instead of building that queue.

65s. The queue point is the one people haven't thought about: a migration that only needs 200ms can still stall the site for a minute, because of what it got stuck behind and what piled up behind it. Gentler NOT NULL if asked: ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID, then VALIDATE CONSTRAINT — that takes a much weaker lock.

§4 Databases · What we did

A backfill script, run in batches

last_id = load_checkpoint()                          # resumable
while True:
    rows = (db.query(Old).filter(Old.id > last_id)     # keyset, not OFFSET
              .order_by(Old.id).limit(1000).all())     # bounded memory
    if not rows:
        break
    with db.begin():                                   # short transaction
        db.execute(insert(New), [map_row(r) for r in rows])
    last_id = rows[-1].id
    save_checkpoint(last_id)                           # safe to restart
    log.info("backfill.progress", extra={"last_id": last_id})
    time.sleep(0.1)                                    # leave room for users
Why id > last_id, not OFFSET: OFFSET 90000 makes Postgres fetch and discard 90,000 rows to hand you 1,000. Keyset paging is an index seek — batch 900 costs what batch 1 did.

A dozen lines, and every one of them is a pattern from earlier in this talk.

Queues, keys, locks, batches — every one of them is invisible until something measures it.

This is the whole talk on one screen, and that is not a coincidence. It pages by keyset rather than OFFSET, so batch nine hundred costs what batch one did. It holds a thousand rows at a time, so memory is bounded. Each batch is its own short transaction. A checkpoint makes it safe to kill and restart. It logs progress, so you can see how far it got. And it sleeps briefly between batches to leave room for the people actually using the product.

§5 Observability · The situation & what it cost

An event system made of database triggers

A logistics product. No message bus — cloud functions watched the database and guessed what had happened by diffing snapshots.

   a row changes ──▶ a function wakes up ──▶ diff old vs new
                                          ──▶ guess what happened
                                          ──▶ decide what to do next
  1. Couldn't track anything — there was no "booking confirmed", only a row that used to look different
  2. Couldn't retry anything — nothing to replay. The reaction was lost, quietly
  3. Couldn't add anything safely — a new feature meant another function diffing the same rows

A logistics product — people booking trucks to move shipments from the port. We had no message bus, so instead cloud functions watched the database for changes and worked out what had happened by comparing the old row to the new one. This was a mistake we made, and it cost us three things. We could not track anything, because there was no "booking confirmed" anywhere in the system — only a row that used to look different, and you cannot count or alert on something that was never named. We could not retry anything, because when a function failed there was nothing to replay; the change had already happened and the reaction was simply lost. And we could not add anything safely, because every new feature meant another function diffing the same rows, hoping it did not collide with the two already doing it.

§5 Observability · What we should have done

Name the event. Publish it. Consume it.

          booking confirmed
                  │
                  ▼
        ┌───────────────────┐
        │ booking.confirmed │   ← an event, with a name
        └───────────────────┘
                  │
        ┌─────────┼─────────┬──────────┐
        ▼         ▼         ▼          ▼
     notify    invoice   analytics   audit log
  • Easier to track — the name is searchable, countable, alertable
  • Easier to retry — the event is a record, so replay it
  • Easier to build — a new feature is just a new consumer
  • Easier to follow — give it an id, carry the id everywhere, and one booking is traceable end to end

Give the thing a name, publish it deliberately, and let anyone who cares subscribe. The name makes it searchable, countable and alertable — "how many bookings were confirmed today" becomes a query rather than an archaeology project. The event is a record, so a failed consumer can replay it, which is exactly why it needs the idempotency key from earlier. A new feature becomes a new consumer, and nothing that already works has to change. And giving each event an id you carry into every consumer and every task argument is what makes one booking traceable end to end across services. The sting is that we already had the outbox available to us — an outbox row is a named event. We just never thought of it that way.

Why the slow 1% isn't 1% of your users

Line every request up from fastest to slowest:

p50    the middle one          — half your requests were faster

p99.9  999 out of 1,000 were faster than this

0.99 ^ 30  =  0.74

   →  26% of page loads hit the slow path.
   →  roughly 1 in 4.

§5 Observability · What to watch

Four things worth instrumenting

  1. Queue depth & oldest-message age — the earliest signal. Latency alerts fire minutes later
  2. p99 per endpoint — a global p99 hides one bad route
  3. Retry & failure rate per dependency — rising retries mean a breaker is about to matter
  4. Slow queries by total time, not average — 100k × 20ms beats the 2-second one you're staring at
And whatever must never be true — alert on it. SELECT count(*) FROM accounts WHERE balance < 0 should be a monitor, not a phone call.

In order of how often they will save you. Queue depth and the age of the oldest message, because that is the earliest signal that work is arriving faster than you drain it — latency alerts fire minutes later. p99 per endpoint, not globally, because a global number hides one bad route. Retry and failure rate per dependency, because rising retries mean a circuit breaker is about to matter. And slow queries sorted by total time rather than average, because a query running a hundred thousand times at twenty milliseconds costs you more than the two-second one you are staring at. And for anything that must never be true — a negative balance, a total that disagrees with its parts — alert on it directly. That should be a monitor, not a phone call from a customer.
