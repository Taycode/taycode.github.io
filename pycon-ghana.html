§2 Processing workloads · What broke

Then we started batching

Core went from sending about 10 items a second to 200,000 at a time.

  • CPU pinned at 100%
  • The automation server restarted, over and over
  • Incoming requests dropped — including the callbacks

Which meant core was now waiting on answers that were never coming.

The work never left the web server

§2 Processing workloads · What we did

Moved it to workers on their own machines

┌──────────────┐      ┌───────┐      ┌──────────────────┐
│ automation   │─────▶│ Redis │─────▶│  celery workers  │ × N
│ (only accepts│      └───────┘      │  (own machines)  │

└──────────────┘                              │
       ▲                                      │
       └────────────── callback ──────────────┘
@app.post("/step-b")

    do_expensive_work.delay(payload.id)
    return {"status": "queued"}

The API server's only job is to accept requests. Concurrency became a number we set, instead of whatever the load happened to be.

Debiting 3,000 accounts at midnight

@cron("0 0 * * *")
def process_mandates():

    results = []
    for mandate in mandates:
        results.append(debit_customer(mandate))      # a network call, each time

A savings product. People set up a mandate; every midnight we move money for all of them. This was one of the first things I was asked to fix.

50s. Real code, simplified. Say the number out loud — three thousand. It was already hurting at three thousand, which is the point.

§2 Processing workloads · What broke, and why

One unit of work was "the whole night"

  1. Blast radius. Mandate #412 raises, and #413 through #3,000 never run.
  2. Retries are all-or-nothing. You can re-run the entire night, or nothing — and re-running debits the people who already paid.
  3. Memory grows with the data. 3,000 objects, plus 3,000 results, held for the whole run.
  4. No visibility. One log line for 3,000 financial operations. Support asks "what happened to this customer?" and you cannot answer.
The usual defence is try/except sprawl around everything — and it still doesn't give you retries.
55s. Point 2 is the one that leads into the next unit — hold it lightly here.

§2 Processing workloads · What we did

One job per mandate

@cron("0 0 * * *")
def enqueue_mandates():
    ids = Mandate.objects.filter(active=True).values_list("id", flat=True)
    for mandate_id in ids:
        process_mandate.delay(mandate_id)      # 3,000 independent jobs

@celery.task(bind=True, max_retries=3, autoretry_for=(ProviderError,))
def process_mandate(self, mandate_id):
    debit_customer(Mandate.objects.get(id=mandate_id))
cron ──▶ enqueue 3,000 jobs ──▶ [ queue ] ──▶ worker  worker  worker
55s. The cron now only decides WHAT runs. Workers do it.

§2 Processing workloads · The concept

Whatever you made a unit of work is the only thing you can retry, observe, or scale.

§2 Processing workloads · What we did

We moved it onto Airflow

A DAG with a schedule, four steps, and nobody's laptop involved.

   ┌─────────┐  ┌───────────┐  ┌──────────┐  ┌──────────────┐
   │ extract │─▶│ transform │─▶│ validate │─▶│ upload to GCS│
   └─────────┘  └───────────┘  └──────────┘  └──────────────┘

     Airflow DAG  ·  scheduled  ·  retry per step  ·  Slack on finish or failure
  • The schedule is in the repo, changed by a deploy — not by remembering
  • Each step retries on its own; a failure at upload doesn't re-run the extract
  • Slack tells us it finished — and tells us louder when it didn't
  • Every run has a history you can open and look at
A task queue could have run the work. It couldn't have given us the schedule, the ordered steps, the per-step retry, or the run history.

§3 Reliability · Why it broke

Why the same work runs twice

A queue normally hands a message to exactly one worker, and most days that is exactly what happens. But what it guarantees is at least once — not exactly once. The gap shows up at failure boundaries.

  1. A retry after a timeout. The call actually went through — you just never got the answer. This is the common one.
  2. A worker dies after the work, before the acknowledgement. The broker never heard "done", so it gives the message to someone else.
  3. A webhook is redelivered. WhatsApp, Instagram and Stripe all document this — you don't get to opt out.
  4. Two schedulers fire the same job. ← what happened to us
  5. The client sends it twice — a double-click, or its own retry.
Most days, none of this happens. That's the trap: "most days" isn't a guarantee, and here it is somebody's money.
65s. Be precise — do NOT claim queues duplicate constantly, because they don't, and someone in the room knows it. The argument is rarity vs. consequence: rare is fine for a thumbnail cache, and not fine for a debit. A distributed lock narrows the window but doesn't close it — if the holder stalls past the TTL, the lock expires while the work is still running. Say this out loud here; it sets up the next slide.

§3 Reliability · The concept

Idempotency, and where the key comes from

Idempotent — running it twice leaves the same result as running it once.

key = str(uuid4())                     # new key every attempt — useless
key = f"{mandate_id}:{run_date}"       # same key every attempt

Derive the key from the work, not from the attempt.

Good keys

  • mandate_id + run_date
  • order_id
  • the provider's message id

Bad keys

  • anything with a timestamp
  • a fresh UUID
  • the hostname or retry count
Some work is idempotent for free: SET balance = 5000, an upsert, a delete by id. Never free: balance = balance + 500, append, send, charge.
60s. Webhooks hand you a free key — the provider's message id. Most immediately useful slide in the talk.

§3 Reliability · What broke, and why

We turned a wobble into an outage

t+0s   provider slows down
t+1s   every worker retries at once   ──▶ provider slows further
t+2s   every worker retries at once   ──▶ provider starts erroring
t+3s   every worker retries at once   ──▶ ...

A fixed retry interval synchronises every client. You have built a coordinated load test against a service that is already struggling.

Meanwhile each worker sits blocked in sleep, so your own queue backs up behind an outage you're helping to cause.

50s. Name it: the thundering herd.

§3 Reliability · What we did

Backoff, jitter, and a cap

@celery.task(
    bind=True,
    autoretry_for=(RequestException,),   # only what's actually retryable
    retry_backoff=True,                  # 1s, 2s, 4s, 8s ...
    retry_jitter=True,                   # randomise, so clients desynchronise
    retry_backoff_max=600,               # stop doubling at 10 minutes
    max_retries=5,
)
def enrich_url(self, url, user_id):
    ...
without jitter   │█│  │█│  │█│      all clients, same instant
with jitter      │ █│▌ │ ▌█│  ▌│    spread across the window

§3 Reliability · The concept

Failing well when a dependency is down

CLOSED  ──5 failures──▶  OPEN  ──60s──▶  HALF-OPEN
   ▲                      │                  │
   └──────success─────────┴───one probe──────┘
  • Circuit breaker. Once you know it's down, stop calling. Fail immediately instead of burning a worker for 30 seconds.
  • Timeouts on every network call. requests defaults to no timeout — one hung socket holds a worker forever.
  • A separate queue per dependency. A backed-up SMS provider must not stop payments from processing.
We split notifications into their own service for exactly that last reason — so a stuck provider couldn't take the core product down with it.

Balances went negative anyway

§4 Databases · Why it broke

The check was correct. It wasn't atomic.

   request A                request B
   ─────────                ─────────
   read balance  5000
                            read balance  5000
   check 5000 >= 4200  ok
                            check 5000 >= 4200  ok
   write balance  800
                            write balance  −4200

Between the read and the write, someone else read the same number. Both requests were individually correct.

This is a race condition: the result depends on the order two things happen to interleave.

60s. Walk the interleaving slowly, line by line. Juniors need the pace.

§4 Databases · What we did

Make the check and the write one operation

-- check and write in a single statement
UPDATE accounts SET balance = balance - :amt
 WHERE id = :uid AND balance >= :amt;     -- 0 rows updated = declined
# or hold the row while you decide
acct = db.query(Account).filter_by(id=uid).with_for_update().one()
-- and a backstop the application cannot forget
ALTER TABLE accounts ADD CONSTRAINT bal_nonneg CHECK (balance >= 0);

The single statement is the right default. The constraint costs nothing and saves you when someone adds a new code path next year.

60s.

§4 Databases · The concept

Stop storing a number you mutate

-- append only. never UPDATE.
INSERT INTO ledger (account_id, amount, reason, idem_key)
VALUES (42, -4200, 'withdrawal', 'wd:918:2026-08-21');

SELECT SUM(amount) FROM ledger WHERE account_id = 42;
  • No read-modify-write, so no lost updates
  • idem_key is unique, so replays are harmless
  • You get an audit trail you didn't have to build separately
Same bug elsewhere: a logistics app incrementing and decrementing counters on every action. Races everywhere. Same fix — stop storing the count, sum the events. Reads cost more; snapshot periodically if that bites. That is caching an aggregate, and you are trading staleness for latency on purpose.
60s.

§4 Databases · The concept

What belongs inside a transaction

Locked for someone else's outage

with db.begin():
    order.status = "paid"
    provider.charge(...)   # 200ms… or 30s
    send_email(...)

Locked for microseconds

with db.begin():
    order.status = "paid"
    db.add(Outbox(
        topic="order.paid",
        payload={"id": order.id}))

A transaction is all-or-nothing — and it holds locks the whole time. Never hold one across a network call you don't control.

Writing the intent in the same transaction, then delivering it separately, is the outbox. One atomic write; the email or the event goes out after.

60s. We stored every notification so we could replay failures — that was an outbox without the name. And a replay is a second execution, so it needs §3's key. End of §4 unit 5 around 23:00.

§4 Databases · Why we couldn't just run it

Two ways the obvious approach fails

1. One big statement takes a lock. A rewrite takes ACCESS EXCLUSIVE — it blocks reads and writes. Worse, it queues behind whatever long query is already running, and the whole app queues behind it.

2. Paging with OFFSET gets slower every page.

SELECT * FROM workspaces ORDER BY id LIMIT 1000 OFFSET 90000;
-- Postgres fetches and throws away 90,000 rows to give you 1,000
SELECT * FROM workspaces WHERE id > 90000 ORDER BY id LIMIT 1000;
-- an index seek. same cost on page 1 and page 900.

Keyset paging needs an index on what you sort by. Equality columns first, then the range and sort columns.

65s. OFFSET is promised in the abstract — this is where it lives, and it's more memorable inside a real migration than as a standalone tip.

§4 Databases · What we did

A backfill script, run in batches

last_id = load_checkpoint()                          # resumable
while True:
    rows = (db.query(Old).filter(Old.id > last_id)     # keyset, not OFFSET
              .order_by(Old.id).limit(1000).all())     # bounded memory
    if not rows:
        break
    with db.begin():                                   # short transaction
        db.execute(insert(New), [map_row(r) for r in rows])
    last_id = rows[-1].id
    save_checkpoint(last_id)                           # safe to restart
    log.info("backfill.progress", extra={"last_id": last_id})
    time.sleep(0.1)                                    # leave room for users

Nine lines, and every one of them is a pattern from earlier in this talk.

65s. Point at each comment: bounded memory (unit 2), safe restart (unit 3), short transaction (unit 5), visible progress (unit 7). Say it isn't a coincidence.

§4 Databases · The concept

Never move data while people are using it

1. EXPAND       add the new column or table — nothing reads it yet
2. DUAL-WRITE   write both, keep reading the old one
3. BACKFILL     in batches, resumable, off-peak
4. CONTRACT     switch reads over, then drop the old one

Four deploys instead of one. Each step is independently reversible, and at no point is there a version of the app that can't read the data.

For indexes, CREATE INDEX CONCURRENTLY builds without blocking writes. It's slower, it can't run inside a transaction, and a failure leaves an INVALID index you have to drop by hand.
50s. CUT CANDIDATE if running long — the script slide is the keeper.

§5 Observability · What broke, and why

We couldn't name our own events

  • No event names. There was no "booking confirmed" anywhere — only a row that used to look one way and now looks another.
  • No ordering, no causality. Which function ran first? Did another one already handle this? Nobody could say.
  • Races. Two functions reacting to the same change, both acting.
  • Debugging meant reconstructing intent from a diff — after the fact, from data that had since changed again.
An outbox row named order.paid isn't just a delivery mechanism. It's the log line you'll want at 3am.
55s. Ties straight back to unit 5's outbox.

§5 Observability · What we did

Name the event, then carry an id through it

log.info("mandate.debit.started",
         extra={"request_id": rid, "mandate_id": mid, "attempt": attempt})
  • Explicit events with names, published on purpose — not inferred from a diff.
  • Structured logs — fields, not prose. You cannot grep a sentence at 3am.
  • One id, carried everywhere — into task arguments, across service calls — so the async half stays connected to the request that started it.
50s. Optional aside if ahead of time: we once chose raw sockets over HTTP between two services assuming HTTP overhead mattered. Never measured it. Cost us status codes, reconnect logic, and any chance of tracing. We optimised the transport, and the transport was never the bottleneck.

§5 Observability · The concept

Averages hide the thing you need to see

1,000 requests: 999 at 50ms, 1 at 30s

mean   =  80ms    ← the dashboard is green
p50    =  50ms    ← still green
p99    =  50ms
p99.9  =  30s     ← what your worst users actually experience

Alert on p99, not on averages. p99 = 99 out of 100 requests are faster than this.

At scale p99 isn't rare. It's everyone, eventually — because one page makes thirty calls.

50s.

§5 Observability · The concept

Four things worth instrumenting

  1. Queue depth and oldest-message age. The earliest signal that work is arriving faster than you drain it. Latency alerts fire minutes later.
  2. p99 latency per endpoint. A global p99 hides one bad route.
  3. Retry and failure rate per dependency. Rising retries mean a circuit breaker is about to matter.
  4. Slow queries by total time, not average. A query running 100,000 times at 20ms costs more than the 2-second one you're staring at.
And whatever must never be true — alert on it. SELECT count(*) FROM accounts WHERE balance < 0 should be a monitor, not something a customer tells you.
