§2 Processing workloads · The situation

Debiting 3,000 accounts at midnight

A savings product. People set up a mandate; every midnight we move money for all of them. This was one of the first things I was asked to fix.

@cron("0 0 * * *")
def process_mandates():
    mandates = Mandate.objects.filter(active=True)   # 3,000 rows in memory
    results = []
    for mandate in mandates:
        results.append(debit_customer(mandate))      # a network call, each time
    send_summary(results)
  1. Blast radius. Mandate #412 raises, and #413 to #3,000 never run.
  2. Retries are all-or-nothing. Re-run the night and you debit the people who already paid.
  3. Memory grows with the data — every row and every result, held for the whole run.
  4. No visibility. One log line for 3,000 financial operations.
70s. Say "three thousand" out loud — it was already hurting at three thousand. Point 4 is the one that actually hurt: support asks what happened to a customer and you cannot answer.

§2 Processing workloads · What we did & the concept

One job per mandate

@cron("0 0 * * *")
def enqueue_mandates():
    ids = Mandate.objects.filter(active=True).values_list("id", flat=True)
    for mandate_id in ids:
        process_mandate.delay(mandate_id)      # 3,000 independent jobs

@celery.task(bind=True, max_retries=3, autoretry_for=(ProviderError,))
def process_mandate(self, mandate_id):
    debit_customer(Mandate.objects.get(id=mandate_id))

That was work trapped inside a loop. The next one had already been moved off the request — or so we thought.

75s. The cron now only decides WHAT runs; workers do it. End on the bridge — it sets up the next story as a twist, not a repeat. Aside if time: same idea one level up — an ETL pipeline as one big script has the same four problems. Split it into steps and you can re-run step 4 alone.

§2 Processing workloads · The situation

Three services, one loop

┌──────────┐         ┌───────┐         ┌──────────┐   HTTP    ┌────────────┐
│   core   │────────▶│ Kafka │────────▶│ gateway  │──────────▶│ automation │
│ (Django) │ publish └───────┘ consume │  (Node)  │  request  │ (FastAPI)  │
│          │                           └──────────┘           └─────┬──────┘
│ owns the │                                                        │
│ sequence │◀──────────── HTTP callback ────────────────────────────┘
└──────────┘         "step 3 done, 812 flagged"

Core publishes "run step 3" to Kafka. The gateway consumes it and turns it into an HTTP request. Automation does the work and calls core back. Core reads the result, decides step 4 is next, and publishes again.

Kafka sits between core and the gateway. But the hop that matters — gateway to automation — is a synchronous HTTP call. The gateway waits for an answer.
60s. Trace all four hops with your hand. Plant the last line hard — the queue is early in the chain and the expensive work is two hops past it. That is the whole failure, and nobody sees it coming.

§2 Processing workloads · What broke

Then core started batching

Core went from publishing about 10 messages a second to dropping 200,000 onto Kafka at once.

core ──▶ Kafka ──▶ gateway ──▶ automation
          200,000     drains      200,000 synchronous
          messages    flat out    HTTP requests
  • Kafka took the burst without blinking — that's its job
  • The gateway drained it as fast as it could, turning every message into an HTTP call
  • Automation's CPU pinned at 100%, and it began restarting in a loop
  • The gateway's requests timed out — and the callbacks core was waiting on were never sent

Core was now waiting on answers that were never coming.

55s. Last bullet is the sting: the failure fed itself, because the callbacks travelled the same broken path.

    label_conversations.delay(req.project_id, req.batch_id)   # hand it off
    return {"status": "queued"}                               # ~5ms

@celery.task(bind=True, max_retries=3)
def label_conversations(self, project_id, batch_id):
    flagged = run_labelling_model(project_id, batch_id)
    core.step_complete(project_id, step=3, needs_review=flagged)   # ← callback

The gateway's call now returns in milliseconds, so it stops mattering how fast it drains Kafka. And the callback comes from the worker that actually did the work — the only thing that knows when it's really finished.

65s. Two moves: the synchronous hop got cheap, and the callback moved to the worker. Concurrency is now a number we set, not whatever the load happens to be.

§2 Processing workloads · What we did next

Not every step costs the same

One queue meant every step queued behind every other step. Stripping PII takes a second. Labelling a batch takes minutes. Put them in the same line and the quick job waits an hour for no reason.

celery_app.conf.task_routes = {
    "tasks.label_conversations": {"queue": "heavy"},   # CPU-bound, minutes
    "tasks.package_dataset":     {"queue": "heavy"},   # big files, lots of memory
    "tasks.strip_pii":           {"queue": "light"},   # quick, high volume
    "tasks.notify_client":       {"queue": "light"},
}
queue: heavy   ──▶  a few large instances      celery -Q heavy -c 4
queue: light   ──▶  many small, shared ones    celery -Q light -c 20

Heavy work got a few big machines. Light work got many small shared ones. And the two scale independently — a labelling backlog adds heavy workers without touching anything else.

60s. Say the shape of the problem first: head-of-line blocking. A one-second job stuck behind a twenty-minute job is pure waste, and it looks like "the system is slow". This is the same isolation idea as bulkheads in the next section — but here it's about matching the machine to the work, not just keeping failures apart.

§3 Reliability · Why it broke

Why the same work runs twice

A queue normally hands a message to exactly one worker, and most days that is exactly what happens. But what it guarantees is at least once — not exactly once. The gap shows up at failure boundaries.

  1. A retry after a timeout. The call actually went through — you just never got the answer. This is the common one.
  2. A worker dies after the work, before the acknowledgement. The broker never heard "done", so it gives the message to someone else.
  3. A webhook is redelivered. WhatsApp, Instagram and Stripe all document this — you don't get to opt out.
  4. Two schedulers fire the same job. ← what happened to us
  5. The client sends it twice — a double-click, or its own retry.
Most days, none of this happens. That's the trap: "most days" isn't a guarantee, and here it is somebody's money.
65s. Be precise — do NOT claim queues duplicate constantly, because they don't, and someone in the room knows it. The argument is rarity vs. consequence: rare is fine for a thumbnail cache, and not fine for a debit. Next slide covers what people reach for to prevent it.

§3 Reliability · The concept

Idempotency, and where the key comes from

Idempotent — running it twice leaves the same result as running it once.

key = str(uuid4())                     # new key every attempt — useless
key = f"{mandate_id}:{run_date}"       # same key every attempt

Derive the key from the work, not from the attempt.

Good keys

  • mandate_id + run_date
  • order_id
  • the provider's message id

Bad keys

  • anything with a timestamp
  • a fresh UUID
  • the hostname or retry count
Some work is idempotent for free: SET balance = 5000, an upsert, a delete by id. Never free: balance = balance + 500, append, send, charge.
60s. Webhooks hand you a free key — the provider's message id. Most immediately useful slide in the talk.

§3 Reliability · The concept

Failing well when a dependency is down

CLOSED  ──5 failures──▶  OPEN  ──60s──▶  HALF-OPEN
   ▲                      │                  │

  • Circuit breaker. Once you know it's down, stop calling. Fail immediately instead of burning a worker for 30 seconds — or send the work to a different provider.
  • Timeouts on every network call. requests defaults to no timeout — one hung socket holds a worker forever.
  • A separate queue per dependency. A backed-up SMS provider must not stop payments from processing.

§3 Reliability · Designing for it

An open circuit is a chance to go elsewhere

def charge(amount, ref):
    for provider in PROVIDERS:                  # primary, then fallback
        if breaker.is_open(provider.name):
            continue                            # known down — skip it
        result = provider.charge(amount, ref)
        record(ref, provider=provider.name, external_id=result.id)
        return result
    raise AllProvidersDown

This only works if you built for it before the outage:

  1. One interface, many adapters. The moment business logic says if provider == "x", failover has stopped being switchable.
  2. Normalise on the way back in. Two providers will not agree on what "pending" means. That translation is your job, at the edge.
  3. Record who processed what — their name, and their reference id.
Point 3 isn't bookkeeping. Refunds, disputes and reconciliation all go back to whoever actually moved the money — and the two providers have different id spaces. Your idempotency key stays yours.

Retries, replays, failovers — every one of them means the same work reaching your data more than once. So the data has to survive it.

75s. More than one payment provider is normal in Nigerian fintech, not exotic — the room will recognise this instantly. Say it plainly: switching providers must never mean charging twice.

§4 Databases · Why it broke

The check was correct. It wasn't atomic.

   request A                          request B
   ─────────                          ─────────
   read balance              5,000
                                      read balance              5,000
   check 5,000 >= 4,200        ok
                                      check 5,000 >= 4,200        ok
   balance = balance - 4,200     800
                                      balance = balance - 4,200  −3,400

Between the read and the write, someone else read the same number. Both requests were individually correct — and ₦8,400 left an account holding ₦5,000.

This is a race condition: the result depends on the order two things happen to interleave.

60s. Walk the interleaving slowly, line by line. Juniors need the pace.

§4 Databases · What we did

Make the check and the write one operation

-- check and write in a single statement
UPDATE accounts SET balance = balance - :amt
 WHERE id = :uid AND balance >= :amt;     -- 0 rows updated = declined
# or hold the row while you decide
acct = db.query(Account).filter_by(id=uid).with_for_update().one()
-- and a backstop the application cannot forget
ALTER TABLE accounts ADD CONSTRAINT bal_nonneg CHECK (balance >= 0);

The single statement is the right default. The constraint costs nothing and saves you when someone adds a new code path next year.

60s.

§4 Databases · The concept

A balance you mutate, or a ledger you sum

A single mutable balance column is the thing every request fights over, and it keeps what the balance is while losing how it got there. One answer is to make the entries the truth and derive the number:

INSERT INTO ledger (account_id, amount, reason, idem_key)
VALUES (42, -4200, 'withdrawal', 'wd:918:2026-08-21');

SELECT SUM(amount) FROM ledger WHERE account_id = 42;

No lost updates, replays are harmless, and you get an audit trail free. But summing every read isn't free either — at a few million entries, on your hottest endpoint, "just derive it" stops being good advice. So most systems keep both:

BEGIN;
  INSERT INTO ledger (...) VALUES (...);
  UPDATE accounts SET balance = balance + :amt WHERE id = 42;   -- same transaction
COMMIT;
The rule isn't "never store it". It's: store it if you need the speed, but make sure you can always recompute it from the entries — and run something that checks the two still agree.
85s. Do not present the ledger as a law — the cost is real. A precomputed balance is a cache and obeys cache rules: it drifts, so it needs a reconciliation job. That check is exactly the invariant to alert on in §5. Aside: a logistics app I worked on incremented counters on every action. Same bug.

§4 Databases · A different system

What belongs inside a transaction

Another fintech. Every withdrawal sends an SMS, and the money moving and the message going out have to agree — we saw both halves fail, separately.

Locked for someone else's outage

with db.begin():
    order.status = "paid"
    provider.charge(...)   # 200ms… or 30s
    send_email(...)

Locked for microseconds

with db.begin():
    order.status = "paid"
    db.add(Outbox(
        topic="order.paid",
        payload={"id": order.id}))

A transaction is all-or-nothing — and it holds locks the whole time. Never hold one across a network call you don't control.

Writing the intent in the same transaction, then delivering it separately, is the outbox. One atomic write; the email or the event goes out after.

60s. We stored every notification so we could replay failures — that was an outbox without the name. And a replay is a second execution, so it needs §3's key.

§4 Databases · The concept

So who actually sends it?

The outbox row is just a row. Something has to pick it up — a relay: a small worker doing one thing, on a loop.

SELECT id, topic, payload FROM outbox
 WHERE published_at IS NULL
 ORDER BY id
 LIMIT 100
 FOR UPDATE SKIP LOCKED;      -- so several relays can run without fighting
for row in batch:
    broker.publish(row.topic, row.payload)     # publish first
    mark_published(row.id)                     # then mark it done

Crash between those two lines and it publishes again — which is at-least-once, and fine, because the consumer already has an idempotency key.

Not a database trigger. A trigger runs inside your transaction and can't safely make a network call — you'd be holding a lock open across the broker. At larger scale, swap polling for change data capture: Debezium tails Postgres' replication log and publishes for you. Lower latency, more moving parts.
70s. This is the slide people actually need — everyone says "outbox" and nobody shows the relay. Order matters: publish THEN mark. The other way round loses events instead of duplicating them, and duplicates are the failure you already handle. SKIP LOCKED callback to the tool table earlier.

§4 Databases · The situation

Moving 100,000 rows on a live product

A marketplace connecting creatives to clients. We changed how workspaces were modelled, and every existing one needed rebuilding — about 100,000 rows — without taking the product down.

The obvious approach is to put it in the migration file:

-- migrations/0042_workspace_v2.sql        workspaces: 100,000 rows

ALTER TABLE workspaces ADD COLUMN owner_id bigint;             -- instant

UPDATE workspaces SET owner_id = legacy_owner;                 -- locks every row,
                                                               -- in one transaction

ALTER TABLE workspaces ALTER COLUMN owner_id SET NOT NULL;     -- full table scan,
                                                               -- blocks reads AND writes

CREATE UNIQUE INDEX ON workspaces (slug);                      -- blocks writes for
                                                               -- the whole build

Four ordinary lines. One is instant. The other three hold your production database while the deploy waits.

70s. Everyone has written this file — that's the point. It isn't reckless, it's normal, and it stops being safe at some row count. If asked: ADD COLUMN with a CONSTANT default is instant on Postgres 11+; a volatile default like gen_random_uuid() still rewrites every row.

§4 Databases · Why it breaks things

A slow migration doesn't just run slowly

  • It's one transaction. Every row that UPDATE touches stays locked until the entire migration commits — not until that statement finishes.
  • Some of it blocks readers too. SET NOT NULL and table rewrites take ACCESS EXCLUSIVE: no writes, and no reads either.
  • Locks queue, and the queue is the real killer. Your migration waits behind whatever long query is already running — and every request that arrives after it waits behind your migration.
SET lock_timeout = '3s';   -- fail fast instead of building a queue behind you
Migrations change structure, and they should be quick. Moving data is a separate job — one that runs in batches, can be paused, and can be resumed. Don't put a hundred-thousand-row UPDATE in a file your deploy is waiting on.
65s. The queue point is the one people haven't thought about: a migration that only needs 200ms can still stall the site for a minute, because of what it got stuck behind and what piled up behind it. Gentler NOT NULL if asked: ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID, then VALIDATE CONSTRAINT — that takes a much weaker lock.

§4 Databases · What we did

A backfill script, run in batches

last_id = load_checkpoint()                          # resumable
while True:
    rows = (db.query(Old).filter(Old.id > last_id)     # keyset, not OFFSET
              .order_by(Old.id).limit(1000).all())     # bounded memory
    if not rows:
        break
    with db.begin():                                   # short transaction
        db.execute(insert(New), [map_row(r) for r in rows])
    last_id = rows[-1].id
    save_checkpoint(last_id)                           # safe to restart
    log.info("backfill.progress", extra={"last_id": last_id})
    time.sleep(0.1)                                    # leave room for users
Why id > last_id and not OFFSET: LIMIT 1000 OFFSET 90000 makes Postgres fetch and throw away 90,000 rows to hand you 1,000 — so every batch is slower than the one before it. Keyset paging is an index seek: batch 900 costs the same as batch 1.

A dozen lines, and every one of them is a pattern from earlier in this talk.

Queues, keys, locks, batches — every one of them is invisible until something measures it.

65s. Point at each comment: bounded memory and batching (§2), safe restart (§3), short transaction and keyset paging (§4), visible progress (§5). Say it out loud — that isn't a coincidence.

§5 Observability · The situation & what it cost

An event system made of database triggers

A logistics product — booking trucks to move shipments from the port. We had no message bus. Instead, cloud functions watched the database for changes and worked out what had happened by comparing snapshots.

   a row changes ──▶ a function wakes up ──▶ diff old vs new
                                          ──▶ guess what happened
                                          ──▶ decide what to do next
  1. We couldn't track anything. There was no "booking confirmed" in the system — only a row that used to look one way. You can't count, search or alert on something that was never named.
  2. We couldn't retry anything. A function failed and there was nothing to replay. The change had happened; the reaction was lost, quietly.
  3. We couldn't add anything safely. A new feature meant another function diffing the same rows, hoping it didn't collide with the two already doing it.
75s. Own it as a mistake — "we built this, and it was the wrong call." Debugging meant reconstructing what someone intended, from data that had since changed again.

§5 Observability · What we should have done

Name the event. Publish it. Consume it.

          booking confirmed
                  │
                  ▼
        ┌───────────────────┐
        │ booking.confirmed │   ← an event, with a name
        └───────────────────┘
                  │
        ┌─────────┼─────────┬──────────┐
        ▼         ▼         ▼          ▼
     notify    invoice   analytics   audit log
  • Easier to track. The name is searchable, countable, alertable. "How many bookings were confirmed today" becomes a query instead of an archaeology project.
  • Easier to retry. The event is a record. A consumer failed? Replay it — which is exactly why it needs the idempotency key from earlier.
  • Easier to build. A new feature is a new consumer. Nothing that already works has to be touched.
  • Easier to follow. Give the event an id and carry it into every consumer and every task argument — then one booking is traceable end to end, across services, in structured logs you can actually query.
60s. Land this: we already had the outbox from the last section available to us. An outbox row IS a named event. We just never thought of it that way.

§5 Observability · What we couldn't see

"The dashboard says it's fine"

A customer says the app is slow. You open the dashboard. Average response time: 80ms. Green across the board. You tell them it looks fine on your end.

You are both telling the truth.

1,000 requests

    999  took     50 ms
      1  took     30 s
   ─────────────────────
   mean          80 ms      ← what the dashboard showed you

The average is real. It just describes a request that never happened to anybody.

50s. Tell it as the conversation — customer says slow, dashboard says fine. Everyone in the room has been on one side of it. One outlier in a thousand moved the mean from 50ms to 80ms and stayed invisible.

§5 Observability · The concept

Why the slow 1% isn't 1% of your users

Line every request up from fastest to slowest:

p50    the middle one          — half your requests were faster
p99    99 out of 100 were faster than this
p99.9  999 out of 1,000 were faster than this

Now: one page load in your app makes 30 API calls. For that page to feel fast, all 30 have to land in the quick 99%.

0.99 ^ 30  =  0.74

   →  26% of page loads hit the slow path.
   →  roughly 1 in 4.

p99 is not your unluckiest customer. It is a quarter of your traffic. Alert on it.

60s. This is the number that makes the point — say it slowly. The intuition people have is "p99 = 1% of users, so who cares". The maths says the opposite as soon as one page makes many calls. If asked: 10 calls -> 10%, 30 calls -> 26%, 50 calls -> 40%.

§5 Observability · What to watch

Four things worth instrumenting

  1. Queue depth and oldest-message age. The earliest signal that work is arriving faster than you drain it. Latency alerts fire minutes later.
  2. p99 latency per endpoint. A global p99 hides one bad route.
  3. Retry and failure rate per dependency. Rising retries mean a circuit breaker is about to matter.
  4. Slow queries by total time, not average. A query running 100,000 times at 20ms costs more than the 2-second one you're staring at.
And whatever must never be true — alert on it. SELECT count(*) FROM accounts WHERE balance < 0 should be a monitor, not something a customer tells you.
